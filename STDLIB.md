# STDLIB.md — Package Substitutions

Every place we'd normally reach for a third-party package, and what we
used from the Python standard library instead.

| I'd normally install | Used instead | Why it works |
|---|---|---|
| `gitleaks` / `truffleHog` (Go binaries) | `re` (regex) + `math` (`math.log2`) | These tools' core detection is regex pattern matching plus entropy scoring. Both are pure computation over strings — no need for a compiled external binary or a package; `re` and `math` cover it fully. |
| `detect-secrets` (Python, pip) | Hand-rolled rule engine in `src/rules.py` | Same underlying concept (a list of named detectors, each returning matches), reimplemented as a plain list of `(name, compiled_pattern, confidence)` tuples with two dispatch functions. No plugin system needed for this scope. |
| Mature vendor-specific secret-scanner plugins | Additional `re` patterns in `src/rules.py` | Expanded standard-library-only coverage for AWS session credentials, Google OAuth, Azure SAS, GitHub/GitLab/Bitbucket, Slack/Discord, Stripe, SendGrid, npm, PyPI, Twilio, Heroku, Mailgun, Shopify, OpenAI, Hugging Face, Databricks, JWT/Bearer/Basic auth, private/PGP key headers, generic credential assignments, authorization headers, and common database credential URLs. This expands coverage without importing a vendor SDK or scanner package. |
| `click` or `argparse` extensions for subcommands | `argparse` (stdlib) `add_subparsers()` | `argparse` already supports `scan` / `install-hook` as first-class subcommands with their own flags — no need for a richer CLI framework. |
| `colorama` / `rich` / `termcolor` | Raw ANSI escape codes (`\033[31m`, etc.) in `src/reporter.py` | Terminal color codes are a well-known fixed set of escape sequences. We check `sys.stdout.isatty()` ourselves to avoid printing raw escape codes into piped/redirected output, which is exactly what these libraries do under the hood. |
| `pathspec` (proper `.gitignore` parsing) | `re` + `os.walk` (stdlib) | Implements ordered ignore rules with `!` negation, directory-only rules, rooted/basename matching, `*`, `?`, `**`, and nested `.gitignore` files without importing a parser. Unusual Git escape corner cases remain out of scope. |
| `pytest` (+ `pytest` plugins for fixtures) | `unittest` (stdlib) | `unittest.TestCase` with `setUp`/`tearDown` covers everything this suite needs: fixture files via `tempfile.mkdtemp()`, assertions, test discovery via `python -m unittest discover`. |
| `pre-commit` (the Python framework for managing git hooks) | A hand-written POSIX `/bin/sh` script, generated by `secretscan.py install-hook` and written straight to `.git/hooks/pre-commit` | We only need to manage one hook for one check, not a multi-hook, multi-language plugin system. The generated hook script (not our Python code) calls `git diff --cached --name-only` itself — that's git's own hook mechanism asking git what's staged, which is inherent to being a pre-commit hook at all, not a dependency we're pulling in. See the "Corrected" note below for why this distinction matters and where we got it wrong. |
| `python-dotenv` | Not used — out of scope | We don't read `.env` files ourselves; the scanner treats `.env` like any other text file and scans its contents for secrets, which is actually the more useful behavior here (catching secrets that *shouldn't* be in `.env` files committed to git). |
| `tomllib` writer / third-party TOML libs (for `.secretscan.toml` config) | `tomllib` (stdlib, read-only, since 3.11) in `src/config.py` | We only need to *read* user configuration, never write TOML, so the stdlib's read-only `tomllib` is sufficient — no need for a writer like `tomli-w` or `toml`. |
| `uuid` generation packages (if we needed scan-run IDs) | `time.strftime()` for timestamps | We only needed a human-readable timestamp for JSON output, not a unique ID — `time` (stdlib) was sufficient, avoided pulling in `uuid` usage where it wasn't actually needed. |
| `jsonschema` (validating our JSON output) | Manual dict construction in `format_json()` | Our JSON output shape is small and fully controlled by us (`json.dumps` on a plain dict) — no external input is being validated, so schema validation would be solving a problem we don't have. |
| Entropy/secret-detection helper packages | `math` + `re` in `src/rules.py` | Shannon entropy is computed directly with `math.log2`; UUID/digest/test-context exclusions and the expanded credential detectors use compiled `re` patterns. No third-party detector or entropy package is required. |
| `watchdog` (for a possible real-time file-watch mode) | Not implemented in this version — documented as a future direction | Considered for a "scan on save" mode; Python's stdlib has no cross-platform file-watching primitive (see capability matrix: "File watching: Python 3.14 = polling"), so a real implementation would need manual `os.stat()` polling. Left out of v1 to keep scope tight and honest rather than ship a half-working watch mode. |

## Detection coverage and entropy update

The detector set was substantially expanded in the latest revision using only Python
standard-library `re` patterns. New coverage includes Google API keys,
Stripe secret keys, SendGrid API keys, npm access tokens, Twilio auth
tokens, Bearer tokens, and common database credential URLs for
PostgreSQL/MySQL/MongoDB/Redis. These additions improve coverage but do
not claim parity with mature scanners.

`.gitignore` handling was also strengthened. The scanner now evaluates ordered
rules, supports negation, directory-only patterns, `*`, `?`, `**`, rooted
patterns, basename rules, and nested `.gitignore` files using only `re` and
`os.walk`.

Shell-history coverage was expanded to common Bash/Zsh/POSIX, ksh/mksh,
Fish, csh/tcsh, and PowerShell/PSReadLine history filenames. History scanning
remains opt-in.

The entropy detector was further hardened against common false positives.
Before entropy scoring it filters UUID-shaped values, conventional fixed-width
hexadecimal digests, machine identifiers/integrity metadata, data-URI payloads,
and clearly marked test/example/fixture values when they are not assigned to a
secret-like field. Secret-like context takes precedence over these exclusions.
This materially reduces common entropy noise while preserving unknown-secret
detection, but zero false positives cannot be guaranteed because entropy is
inherently a heuristic.

Both updates use only the Python standard library; no third-party runtime
dependency was added.

## Corrected: a real dependency-hiding bug we found and removed

An earlier draft of this tool added a `--staged-only` scan flag whose
implementation, in `src/scanner.py`, called `subprocess.run(["git",
"-C", ..., "diff", "--cached", ...])` **directly from Python** to
figure out which files were staged. That is exactly the thing the
event rules forbid: *"Can my tool run git, CMake or another installed
tool at runtime? A: No. Invoking a separately installed tool is a
dependency you would be hiding."* It also failed dangerously — if git
wasn't on `PATH`, or the directory wasn't a git repo, the flag
silently reported "No secrets found, exit code 0" instead of erroring,
which is the worst possible failure mode for a security tool.

Fix: `--staged-only` has been removed entirely from the Python CLI.
Staged-file scanning is now handled *only* by the installed git hook
(a shell script git itself executes during `git commit`), which asks
git for the staged-file list in the hook script and hands that list
to `secretscan.py scan file1.py file2.py ...` as ordinary positional
arguments. `secretscan.py` and every module under `src/` now contain
zero calls to `subprocess` and have no knowledge that git exists.
`deps-proof.txt` was also stale (it only scanned 4 of the 6 shipped
source files and would have missed this) and has been regenerated to
cover every file we ship.

## Corrected: a hook that shelled out safely but not correctly

The generated `.git/hooks/pre-commit` script never called `subprocess`
from Python — that part was always right (see above). But the shell
script itself had a real bug: it captured the staged-file list from
`git diff --cached --name-only` into a shell variable and expanded it
unquoted (`scan $STAGED_FILES`). POSIX shell word-splits an unquoted
expansion on whitespace, so a staged path with a space in it broke
into multiple bogus arguments, and a filename starting with `-` could
be parsed by `argparse` as an option flag instead of a path — neither
is a hypothetical, both are exactly the kind of filenames real
projects have (`"design assets/-draft.env"`, `node_modules` packages
with scoped names, etc).

Fix: the hook no longer puts filenames in a shell variable at all.
`git diff --cached --name-only --diff-filter=ACMR -z` streams
NUL-delimited output straight through `xargs -0` into
`secretscan.py scan --`, and a separate `git diff --cached --quiet`
probe (which touches no filenames) decides whether there's anything
staged in the first place. `--` guarantees every following argument
is treated as a path by `argparse`, never as an option. Still zero
`subprocess` calls from Python, still git's own hook mechanism asking
git what's staged — just correct shell quoting on top of it. Covered
by `TestPreCommitHookIntegration` in `tests/test_scanner.py`, which
installs the real hook into a throwaway git repo and commits a file
literally named `-weird secret.env` to prove it.

## package killer candidate

**Target:** `detect-secrets` (PyPI) — a widely used pre-commit secret
scanner from Yelp, commonly installed via `pip install detect-secrets`
and used in CI pipelines and pre-commit hook configs across many open
source and internal company repos.

**What we reimplemented:** the core detection loop — pattern-based
rules for known secret formats across cloud, source-control, AI/LLM, CI/CD, developer-platform, messaging, database and authentication families, plus generic quoted/unquoted credential assignments and entropy-based detection for
unknown/custom formats, redacted output, and git pre-commit hook
installation — all without needing `pip install` at all.

**What we didn't reimplement** (honest scope limits): `detect-secrets`
also supports a plugin architecture for custom detectors and
integration with several secret-management platforms.
`secretscan` is intentionally narrower — a single-purpose, zero-setup
scanner rather than a full platform. (We *do* implement a baseline
file — `--update-baseline` writes accepted-finding fingerprints to
`.secretscan-baseline.json`, and `apply_baseline()` in
`src/scanner.py` filters them out of future scans — an earlier draft
of this note incorrectly listed that as unimplemented.)

## Build tooling

`build_single_file.py` (the script that produces `dist/secretscan_single.py`
for the Single File bonus) uses only `ast` and `pathlib` — both stdlib. We
considered pulling in a templating or code-generation package, but the
merge itself is simple text/AST surgery (strip local imports, concatenate
module bodies in a fixed dependency order, dedupe external imports), which
stdlib `ast` handles directly.

## Design choices worth noting

- **No cipher implementation of any kind.** This tool only *detects*
  patterns and measures entropy — it never encrypts, decrypts, hashes
  for security purposes, or implements any cryptographic primitive. This
  keeps it fully outside the "never roll your own cipher" concern.
- **Redaction is always-on**, not a flag you have to remember to pass —
  the `Finding.redacted()` method is the only way findings are ever
  rendered to the user, so a full secret can't accidentally leak into
  terminal history or CI logs.
